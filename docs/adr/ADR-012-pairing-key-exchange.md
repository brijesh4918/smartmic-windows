# ADR-012 — Pairing Key Exchange: CPace over ristretto255

**Status:** Accepted · **Date:** 2026-09-12 · **Requires security review before release**

## Context

ADR-005 requires a PAKE so that a 6-digit code cannot be attacked offline.
libsodium — the crypto library available on every platform this product targets
— does not ship a PAKE. It does ship ristretto255 group operations
(`crypto_core_ristretto255_from_hash`, `crypto_scalarmult_ristretto255`), which
are exactly what a balanced PAKE needs.

## Decision

Implement **CPace** over ristretto255:

```
  both sides:  G  = map_to_group( H(code ‖ sessionId ‖ associatedData) )
  each side:   y  <- random scalar
               Y  = y · G                       (exchanged)
  both sides:  K  = y · Y_peer
               sk = HKDF( K ‖ transcript )
```

Then each party signs the full transcript (including both long-term Ed25519
public keys, both CPace messages and the protocol version) with its long-term
key, and the peer verifies.

The code never appears on the wire, and a passive observer learns nothing
testable about it — recovering it requires solving a discrete log per guess, so
the only attack is online, which the 5-attempt / 300 s limiter caps.

## Alternatives

1. **MAC the transcript with a key derived from the code.** Trivial to build on
   libsodium, and catastrophically wrong: a passive observer captures one
   handshake and tries all 10⁶ codes offline in milliseconds. Rejected, and
   recorded here because it is the obvious-looking shortcut.
2. **SPAKE2.** Equally valid; needs two fixed group elements generated by a
   nothing-up-my-sleeve procedure, which is more ceremony than CPace for no
   benefit here. CPace is also the CFRG-selected balanced PAKE.
3. **OPAQUE / asymmetric PAKE.** Solves a problem we do not have (there is no
   long-lived password and no server-side password file). Rejected.
4. **Vendor a third-party PAKE implementation.** Preferable to writing one, and
   should be revisited before release; at the time of writing there is no
   maintained, permissively licensed C implementation that covers all three
   target platforms as cleanly as building on libsodium's own primitives.

## Tradeoffs

This is protocol code built on reviewed primitives rather than a reviewed
protocol implementation. That is a real risk and is why this ADR carries an
explicit gate: **an external cryptographic review of `pairing.cpp` is a
release-blocking item**, tracked in the Phase 7 security review.

## Failure modes

- Invalid group element from the peer → `crypto_scalarmult_ristretto255` returns
  non-zero and the exchange is aborted. Never ignored.
- Identity element / small subgroup → ristretto255 has no small subgroup and
  rejects the identity, which is why it was chosen over raw Curve25519 here.
- Code reuse across sessions → the code is bound into `G` together with the
  per-session `sessionId`, and is destroyed on first use.

## Security implications

Compromise of one pairing does not affect others: each derives an independent
session key, and long-term identities are per-device. The transcript signature
is what upgrades CPace's "we share a code" into "I know which device you are",
and it is what makes QR fingerprint verification meaningful.
